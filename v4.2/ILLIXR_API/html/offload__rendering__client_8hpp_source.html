344 // Maximum number of encoded frames allowed in the color decoder input
345 // queue before incoming frames are dropped to prevent growing latency.
346 // At 90fps a frame arrives every ~11.1ms; the feeder thread's
347 // dequeueInputBuffer has a 2ms timeout and may loop several times per

363 // Bounds how many submitted dual_frames are kept alive awaiting release.
364 // Rather than requiring an explicit GPU-completion signal from the
365 // render-side consumer (oxr_interface), a submitted frame's
366 // AHardwareBuffers are released once this many *newer* frames have been
367 // submitted after it - i.e. once enough real time has passed that the
368 // render pass reading it is essentially certain to be done. At the
369 // slowest supported refresh rate (72Hz, ~13.9ms/frame) this guarantees
370 // at least ~139ms between a frame's submission and its release; at 90Hz
371 // it's ~111ms. The render-pass read itself takes on the order of a few
372 // ms, so this leaves a wide margin under normal operation. A sustained
373 // render stall longer than this window could still release a buffer
374 // while the GPU is reading it; if corruption is ever suspected, that's
375 // the first thing to check (e.g. via frame-pacing logs around the same
376 // time) before raising this value further.
